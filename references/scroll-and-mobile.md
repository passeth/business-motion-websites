# 스크롤 모션과 실제 모바일

## 한 가지 ‘모션’으로 취급하지 않는다

| 동작 | 시간의 기준 | 제어 |
|---|---|---|
| 분위기 영상 루프 | 미디어 재생 시간 | muted/inline/loop, 사용자 정지, 가시성 |
| 프레임 스크러빙 | 구간의 스크롤 위치 | target time, 디코더 준비, 앞/뒤 탐색 |
| 구간 진입 등장 | 최초 진입 또는 재진입 | 완료 상태 유지, 빠른 스크롤 대응 |
| 설명용 연결선 | 정보의 순서·관계 | SVG path/노드 강조, 의미와 일치 |
| UI 피드백 | 선택·펼침·승인 | 인접 상태 변경, 짧은 전환 |

사용자가 자동재생 루프를 원했으면 모든 영상을 스크롤 탐색으로 바꾸지 않는다. 특정 구간의 프레임 연동 요청을 전체 사이트의 동작으로 확장하지 않는다.

## 스크롤 장면 설계

- 하나의 유한한 장면 구간과 sticky stage를 둔다. 긴 비어 있는 스크롤과 스크롤 가로채기를 피한다.
- 입력은 기본 스크롤을 사용한다. 페이지 안에서 휠·터치를 별도 가속 곡선으로 덮어쓰지 않는다.
- 진행률의 예: `p = clamp((scrollY - sectionTop) / max(1, sectionHeight - stageHeight), 0, 1)`.
- 목표 시각: `target = p × max(0, duration - frameInterval)`. 메타데이터가 오기 전 duration을 가정하지 않는다.
- 레이아웃 변화·주소창·방향 전환으로 구간 치수가 달라지면 다시 계산한다. 실제 모바일의 svh/dvh 차이를 보고 stage 높이를 선택한다.
- 수동 재생과 스크롤 탐색이 동시에 currentTime을 쓰지 않도록 모드 소유권을 정한다.
- 비활성 텍스트 패널은 포인터·키보드·스크린리더 접근 상태도 맞춘다. 보이는 글만 바꾸고 숨은 링크가 포커스되는 상태를 피한다.
- 중요한 문구는 읽을 시간과 대비를 확보한다. 스크롤을 아주 천천히 해야만 문장을 볼 수 있다면 구간 설계를 수정한다.

## 영상 탐색과 대안

Native MP4를 쓴다면 Range 응답, 적합한 코덱, 파일 크기, 키프레임 간격과 디코딩 비용을 검토한다. 스트리밍 시작을 돕는 faststart와 탐색 비용을 줄이는 인코딩은 크기와 품질의 절충이 있으므로 측정 후 선택한다.

requestAnimationFrame으로 업데이트를 합치고, seek가 진행 중일 때 끝없는 seek 요청을 쌓지 않는다. 마지막 요청한 목표를 유지하고 준비/seeked 시점에 필요한 탐색을 이어간다. `currentTime` 변화만으로 화면 프레임 갱신을 주장하지 않는다. 가능하면 requestVideoFrameCallback이나 디코딩된 프레임 캡처로 확인한다.

영상 탐색이 실제 기기에서 불안정하고 해당 장면이 핵심이면 이미지 시퀀스/canvas 방식을 검토한다. 시퀀스는 파일 수·메모리·디코드·캐시 비용이 커질 수 있으므로 인근 프레임 로딩, 메모리 해제와 모바일 해상도를 설계한다. poster-only 대안을 제공하되 이를 동일한 스크롤 구현으로 보고하지 않는다.

## 재생 상태 모델

최소한 아래 원인을 구분한다:

`대기/로딩 · 재생 중 · 브라우저 정책 차단 · 사용자가 정지 · 화면 밖/탭 숨김 · 모션 감소 · 파일/디코드 오류`

- `play()` 거절을 사용자의 정지 의사로 저장하지 않는다.
- muted·playsInline을 소스와 재생 요청 전에 설정한다. 모바일에서 허용되는 직접 클릭/터치 안에서 load/play 초기화를 시도하고, await 체인 때문에 사용자 활성화가 사라지지 않는지 확인한다.
- 스크러빙의 디코더 초기화에 잠깐 재생이 필요했다면 준비 후 탐색 모드로 돌려놓는다. 이 절차는 기기에서 확인하고 불필요한 반복을 피한다.
- 사용자가 직접 정지한 영상은 스크롤 재진입이나 탭 복귀로 임의 재생하지 않는다.
- 가시성·페이지 복귀·모드 변화 시 기존 상태와 리스너를 재사용한다. 재생 루프·이벤트 리스너가 중복 생성되지 않게 정리한다.
- 하나의 전역 ‘모든 영상 정지’ 처리 대신 gallery, background, scrub의 책임을 분리한다.

## 모션 감소

CSS와 JavaScript가 같은 설정을 따른다. reduced-motion에서는 완성된 도표와 읽을 수 있는 본문을 보여준다. 사용자에게 사이트 내 모션 켜기 선택을 제공할 수 있지만 명시적 선택이어야 하며 다시 끌 수 있어야 한다. OS 설정을 바꾸지 않는다.

처음부터 전환을 강제로 활성화하거나 iPhone이라는 이유로 모든 모션을 정지시키지 않는다. 접근성 선택과 재생 실패는 원인이 다르다. 짧은 영상 재생 버튼, 정지, 접근성 라벨은 남기되 ‘스크롤 엔진 복귀’ 같은 내부 구현 설명은 노출하지 않는다.

## SVG/연결 인포그래픽

객체·관계·순서를 먼저 정의한 후 경로 그리기, 흐르는 강조, 노드 확대, 승인 지점의 대비를 배정한다. 그림과 텍스트의 읽는 순서를 일치시킨다. Quantity/Quality/Possibility와 같은 가치 분류를 쓰더라도 각 그래픽이 설명하는 변화가 달라야 한다.

화면 밖에서는 정지한다. 모션 감소에서는 관계가 완성된 정적 도표를 보여준다. 등장 효과의 opacity가 클릭 결과나 레이아웃 재배치와 결합해 내용을 흐리게 남기지 않는지 확인한다.

## 모바일 정보 구조

데스크톱 탭이 왼쪽 목록/오른쪽 설명이라면 모바일에서 결과가 여러 화면 아래 나타날 수 있다. 다음 중 실제 읽기에 맞게 선택한다:

- 선택한 항목 바로 아래에 상세를 펼치는 단일 열 구조.
- 결과 위치가 충분히 가까운 짧은 탭 패널.
- 공유·길이 요구가 큰 경우 별도 상세 페이지.

아코디언으로 바뀌면 button/region, aria-expanded/controls, 포커스 상태도 맞춘다. 데스크톱 tablist 역할을 의미 없이 남기지 않는다. 화면 폭을 바꿔도 선택 내용·포커스·열림 상태가 예측 가능해야 한다.

## 기기 검증 순서

1. 데스크톱 정상/모션 감소, 키보드, 앞·뒤 스크롤.
2. 작은 화면과 태블릿에서 내비게이션·모달·선택 결과 위치·회전.
3. 모바일 브라우저 엔진에서 자동재생 거절·재시도·포스터·정지 복귀.
4. 접근 가능한 실제 휴대폰에서 로딩 → 터치 → 프레임 변화 → 이탈/복귀 → 정지 → 설정 변화 확인.

데스크톱 반응형 모드, 데스크톱 WebKit, 실제 iPhone은 서로 다른 증거다. 실제 기기 접근이 없으면 에뮬레이션 범위와 남은 확인을 명시한다. ‘iPhone 검증 완료’로 확대하지 않는다.

모바일 검증에서 얻은 교훈: 실제 iPhone의 정지 상태에는 모션 감소 설정이 관여했고, 재생 정책 차단과 사용자의 정지를 구별하는 처리도 필요했다. 동시에 선택 상세가 모바일 하단 멀리 나타나는 문제를 인접 펼침으로 개선했다. 같은 증상이라도 원인은 재측정한다.
