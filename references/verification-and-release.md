# 검증·검색·배포·인수

## 완료 증거를 단계별로 분리한다

| 주장 | 필요한 증거 |
|---|---|
| 사이트를 구현했다 | 실제 페이지와 핵심 사용자 흐름 |
| 이미지를 생성했다 | 결과 파일과 원본/출처 기록 |
| 영상을 렌더했다 | 최종 영상 메타데이터·디코딩 프레임·연속 재생 |
| 나레이션을 넣었다 | 최종 배포 파일의 오디오와 실제 청취 |
| 모바일에서 작동한다 | 어떤 기기/브라우저에서 어떤 행동을 확인했는지 |
| 배포했다 | 공개 URL, 실제 콘텐츠, 올바른 프로젝트/도메인 |
| 문의가 접수된다 | 실제 수신/저장 확인; 초안 열기와 구분 |
| SEO를 설정했다 | 공개 HTML·대표 URL·사이트맵·수집 허용 |
| 검색 성과가 있다 | 계정의 실제 색인·쿼리·유입 또는 관찰한 인용 |

## 페이지와 상호작용

변경한 범위의 페이지를 빠뜨리지 않도록 먼저 목록을 만든다. 공유 헤더·푸터·CSS를 바꿨으면 사용 페이지에 미치는 영향을 확인한다.

- 폭이 작은 휴대폰, 태블릿, 넓은 데스크톱에서 제목·본문·내비게이션·버튼·다이얼로그를 확인한다.
- 한글의 마지막 글자, 긴 전문 용어, 단어 하나가 남는 줄바꿈, 글자 잘림·폰트 누락을 실제 이미지에서 확인한다.
- 키보드 포커스, Escape, 상세를 닫은 뒤 포커스 복귀, 모달 뒤 배경 스크롤, 메뉴 열기·닫기를 확인한다.
- 필터는 초기 상태·직접 URL·선택·해제·뒤로 가기·상세 열기·닫기를 검증한다.
- 폼은 잘못된 입력, 정상 입력, 실제 처리 목적지, 파일 다운로드·mailto 등 대체 동작을 검증한다. 외부 테스트 전송은 사용자의 권한 범위를 확인한다.
- 콘솔 오류, 리소스 404, 잘못된 링크, 가로 넘침과 사용 중 누적되는 재생/리스너를 확인한다.

UI가 달라진 구간을 새로 캡처한다. 긴 전체 캡처만으로 작은 한글을 판정하지 말고 대표 화면 크기로 잘라 읽는다. 가능한 독립 검토를 활용하되, 별도 리뷰 워크플로 전체를 작은 수정마다 자동 실행하지 않는다. 현재 환경의 필수 QA 지침이 있으면 따른다.

## 미디어와 성능

- 실제 전달 파일에서 시작·중간·전환·끝 프레임, 루프 경계, 글자 체류 시간과 오디오를 확인한다.
- 영상 위 카피의 대비는 대표 포스터뿐 아니라 가장 밝고 복잡한 프레임에서 확인한다.
- 첫 화면의 핵심 미디어만 우선 로딩하고 나머지는 인근 가시성에 따라 로딩한다. 이미지 크기 선언과 적절한 해상도로 불필요한 이동을 줄인다.
- 느린 네트워크/파일 실패 시에도 제목·설명·CTA가 남는지 확인한다.
- 요청 수·전송량·메모리·프레임 정체를 실제 페이지에서 확인한다. Lighthouse 점수만으로 실기기 영상 재생이나 체감 성능을 단정하지 않는다.
- 측정 예산은 사업/기기/미디어에 맞춰 정한다. 한 프로젝트의 영상 개수·길이·코덱 옵션을 보편적 정답으로 고정하지 않는다.

## SEO/AEO

검색 설정이 요청 범위에 포함되면 적용한다. 일반적인 공개 사이트에서는 기본 메타데이터와 읽을 수 있는 본문을 제작 과정에 포함한다.

1. 고객·업무·구매 의도를 결합해 키워드를 페이지에 배정한다. 검색량 도구가 없으면 정량 수요를 만들지 않는다.
2. 제목·설명·H1·대표 URL을 고유하게 관리하고 내부 링크를 연결한다. 연관 파라미터와 확장자 URL이 중복 대표 페이지가 되지 않게 한다.
3. 핵심 정보와 사례가 JS 실행이나 영상 재생에만 의존하지 않게 서버/정적 HTML로 제공한다. HTML과 클라이언트 데이터가 같은 원본에서 생성되도록 하는 편이 장기 유지관리에 좋다.
4. 공개 도메인의 robots.txt와 sitemap.xml, 이미지 공유 메타데이터를 확인한다. 테스트 환경과 비공개 환경의 noindex를 혼동하지 않는다.
5. Organization·WebPage·Service·Article 등 실제 내용을 설명하는 구조화 데이터를 사용한다. 가짜 평점·고객 실적·직원 경력은 넣지 않는다.
6. 답변형 콘텐츠는 질문 직후 명확한 답, 조건, 절차, 근거를 둔다. 작성 조직·실제 검토일을 표시한다. 키워드 반복을 위해 유사 문서를 양산하지 않는다.
7. Google Search Console·네이버 소유 확인·사이트맵 제출과 분석 도구 연결은 실제 계정/인증값이 있어야 완료된다. 준비한 파일과 외부 등록 상태를 구분한다.

최신 정책은 구현 시 공식 문서를 확인한다: [Google AI 검색](https://developers.google.com/search/docs/appearance/ai-features), [Google 변경사항](https://developers.google.com/search/updates), [네이버](https://searchadvisor.naver.com/guide/seo-basic-intro), [OpenAI 검색 크롤러](https://developers.openai.com/api/docs/bots).

AI 전용 파일이나 특정 스키마가 답변 인용을 보장한다는 전제를 두지 않는다. FAQ 리치 결과와 같은 지원 기능은 바뀔 수 있다. 크롤링 허용과 모델 학습 정책을 같은 것으로 취급하지 않는다.

## 배포와 도메인

현재 프로젝트의 Git remote, 브랜치, 호스팅 project, 배포 출력 폴더, 도메인 연결을 확인한다. 대화에 예전 Sites 링크와 현재 Vercel 도메인이 함께 있으면 실제 운영 대상을 구분한다.

사용자가 이미 승인한 배포는 반복 승인 없이 진행한다. 별도 프로젝트의 승인까지 새 고객·도메인의 구매/배포 권한으로 확장하지 않는다. 유료 도메인 구매·미승인 외부 공개 등 새로운 행동은 현재 범위를 따른다.

- 테스트 결과가 있는 변경만 올리고 기밀 파일·자격 증명·개인 고객 자료를 제외한다.
- Git push, 호스팅 성공, 도메인 반영을 각각 확인한다. 관리 API 인증이 만료돼도 Git 연동 배포가 성공할 수 있으므로 실제 상태를 조사한다.
- 공개 URL의 HTML·정적 파일·새 경로·리다이렉트·미디어 Range 응답을 검증한다.
- 구 버전 캐시와 다른 프로젝트를 혼동하지 않도록 커밋/배포 식별자와 실제 파일을 대조한다.
- robots·sitemap·canonical을 로컬 호스트로 배포하지 않는다. 404를 무조건 홈으로 보내는 설정을 피한다.

## 인수와 개선

운영자가 수정할 위치를 짧게 남긴다: 사업 문구, 프로그램, 사례, 미디어 교체·포스터, 문의 목적지, 검색 메타데이터. 영상 원본/편집 프로젝트·폰트 라이선스·재렌더 방법도 보관한다.

다음 릴리스는 관찰한 문제나 실제 검색·상담 데이터에서 시작한다. ‘동적이라 멋져 보인다’보다 고객이 사업을 이해하고 적절한 다음 행동을 할 수 있는지 검토한다. 사용자의 별도 요청 없이 예약 모니터나 자동 생성 작업을 만들지 않는다.
